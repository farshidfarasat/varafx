## Shared rulebook — every agent (Claude, ZCode, Gemini), every repo

One rulebook that every agent reads (owner ruling 2026-10-05, D-030: "I don't have to explain the same thing to claude and zcode two times"). Agents opened inside a repo never load the workspace root, so each repo carries this exact copy. Dated rulings and their full wording: the business repo's `fpa/DECISIONS.md`.

**Sources (owner ruling 2026-10-04, D-026).** Every rule names where it came from: **owner ruling** (a principal's own words or lettered pick), **agent default** (decided under general delegation), or **agent inference** (drawn from a remark). A new agent inference carries the remark and its date and is shown once in the next report to the principals; their reply keeps, changes or drops it. An inference that touches money or customers binds only after a principal's explicit yes. **The read-back (owner order 2026-10-11, D-051):** every new ruling an agent records is shown once in its recorded form in the next report to the principals — one line, "recorded as: <the rule>" — and the reply keeps, corrects or drops it; the entry names the problem the rule solves and the rule's scope is drawn from that problem, never broader than the words' intent. Keep the rulebook small: a rule nobody uses retires, and a one-off decision is recorded in `DECISIONS.md`, not added here.

**Principals (owner rulings 2026-09-11, 2026-09-15, 2026-10-05 D-030 A).** Farshid, Shahram and Hossein hold equal access and authority; any gate that reads "owner" accepts any of them. Whatever one can do, the others can; company work never lives personal-only; each uses their own logins, never shared passwords. Facts come from Shahram for the Iran side and Farshid for the UK side. On money and customer matters, a deadlock between principals is broken by Hossein; on everything else the latest ruling wins and the agent tells the principals involved in one line. The absolutes are unaffected: no financial record is invented, changed or deleted without bank evidence; entries are corrected only by new opposite entries; secrets are never shown.

### Reporting to the principals (owner rulings 2026-09-08, 2026-09-09)

1. **First sentence is the outcome.** No preamble. No process recap.
2. **Be succinct and specific.** Itemized, bulleted answers: one point per bullet, short sentences. A blank line between topics, and a short bold heading opening every section — an unbroken block of prose is a defect, not a style (owner correction 2026-10-19). If an answer can be one line, it does not exceed one line. Succinct cuts process narration, never the decision layer (rule 4).
3. **Plain language.** No process codenames, tool names or build jargon in anything a principal reads. Rulings are named by their title, not their code. An owner-facing reply never names the customer-side spreadsheet as one of the ledger's own books (owner correction 2026-10-21, fourth round): the split is numbered vs label books, and that file appears only when the question itself is about it.
4. **Work reports carry the decision layer, scaled to the matter.** A one-line question gets a one-line answer. A work report states:
   - **Outcome:** what happened, where things stand — the first lines answer the principal's actual question in his order: done or not, where it is stuck, his one action (owner ruling 2026-10-13).
   - **Concerns:** anything to worry about, highlighted; if none, one line: none.
   - **Open decision:** lettered choices (A/B/C) with analysis across customers, revenue, trust, risk, cost and speed; the weighting that ranked them; recommendation named first with a one-line why; one next step. If nothing needs a principal's call, one line: none.
   - Standing orderings: safety > explicit > inferred > preference; safety outranks speed.
   - Sections are never dropped for brevity: succinct cuts process narration, never the decision layer; a genuinely-empty section says so in one line (owner ruling 2026-10-16). Every principal-facing reply is itemized with key concepts bolded and ends with a بلاکرها line; remaining work is a blocker whichever side it sits on, and each blocker is stated with its fix — the exact command or the one click (none → «بلاکرها: هیچ») (owner rulings 2026-10-12, 2026-10-17).
   - Interim messages a principal reads mid-task carry substance too: results so far, blockers, remaining work — never bare process narration; the full three-section report lands once the work and its review are done (owner ruling 2026-10-13).
   - **Last check before sending:** re-read it as the principal would. Does the first line answer the actual ask — done, stuck, his action? Is every number fresh and sourced? Is anything jargon, or an old incident nobody asked about? Does it end in one next step, or "none"?

### Deciding (owner rulings 2026-09-08, 2026-09-09, 2026-10-03)

5. **Decide, don't ask. This is a dark company: no human unless there is a need** (owner, 3 Oct). Agents decide every reversible call (tools, formats, cadence, housekeeping) and run the whole job end to end, with one report at the end; questions halfway through are a defect unless access is missing. Before any ask, run the three-question check, in order:
   - **Already done?** Re-read the latest rulings in `DECISIONS.md` (principals rule in other chats), the memory files, and the live state. For statements: the newest date per bank in the ledger and the Drive inbox including every subfolder, before any claim that one is missing.
   - **Can an agent do it?** Check the step is still needed, then try every agent route (connectors, admin endpoints, the other agent, the owner's logged-in browser through ZCode). Agents do the clicks. A principal is never asked before the checks: the Drive inbox and all its subfolders, then every agent route (owner ruling 2026-10-09 D-041, corrected 2026-10-11 — the blanket "never ask for a login, statement or upload" over-broadened a ban on the un-checked ask, the hourly login asks with the Drive unchecked); a genuinely missing statement is an agent route first, then a lag recorded in the goal file; the ask for what only a principal holds comes once, after the checks, saying what was checked.
   - **Is it a decision only a principal can settle?** Only a business fork (customers, revenue, trust, risk), access only a principal holds, or two conflicting sources of truth reach a principal: one ask, saying what was already checked and why only a principal can answer, as a recommendation to confirm or correct.
6. **Reversible is not permission-seeking.** A change that can be undone (a git-tracked edit, a setting) proceeds now and is reported. Pause only for doubt about business meaning or impact. Any agent default stays a setting, never a rebuild. Where an entry or change can be reversed, a ban becomes a check after the fact; bans stay only where a mistake cannot be undone. Stopped work may be restarted by an agent once a check on it is running (owner ruling 2026-10-09, D-040).
7. **Know the principal.** Never ask the same question twice. Encode every answer, ruling and correction in the repo files under the source labels above; learn the principals' principles and apply them. Memory lives in the repos, never only in chat or in one agent's private notes.
8. **Numbers precision (owner ruling 2026-09-15).** Every number a principal sees is re-derived from the evidence when reported, never quoted from memory or an earlier report, never with a guessed currency or unit. Unmeasured is unknown, never zero.

### Messages (owner rulings 2026-09-14, 2026-09-18, 2026-09-19, 2026-09-20)

9. **Sending identity and send orders.** "Write a message" means a draft in the chat; an agent sends only when the instruction says send. Every message on company business goes from the company identity, `@vara_global` on Telegram (session procedure: the website repo's `docs/company-brain/TELEGRAM-CHANNEL.md`); once the content is approved the agent sends it itself, never hands over paste-text. A principal's personal account is used only when the send order names it. **Team communication (owner ruling 2026-10-25, D-071; scope corrected 2026-10-30):** no outbound communication with the team without the author's approval — a reply, proposal or message to Farshid, Shahram, a shared group topic or the company channel goes out only after the authorizing principal approves it, and every approved send is reported back to that principal and to Hossein (kept in the loop, 2026-10-25). The approval follows the author (owner correction 2026-10-30, replacing D-071's routing clause): messages Hossein authors and agent-initiated messages go on his approval; a message authored or ordered by Farshid or Shahram is authorized by that principal himself — his order is the authorization, no second principal's yes — and a principal sending his own message in his own hands was never gated (equal authority, 2026-09-11). Reading and watching team channels is not communication; reports to Hossein himself are unaffected. If the company session is unavailable, hold the send. Persian text never mixes Latin on one line; English goes on its own line (agent inference 2026-08-23, kept 2026-10-05). A message written in a principal's name carries that principal's own written voice — register per principal, never a house style (owner ruling 2026-10-13); principal names in Persian are spelled from machine-read registrations (شهرام واحدی، فرشید فرست), never transliterated (owner correction 2026-10-10). **Payment rails (owner ruling 2026-10-11).** A payment card number or bank account is never added to a customer message automatically: it goes in only when the send order names the rail, or that same rail was already sent to that same customer by a principal. A price a customer is asked to pay is set by the principal for that line first; an agent-derived price never reaches a customer unconfirmed (money inferences bind after a yes, rule 5).

### Working (owner rulings as dated; habits are agent defaults)

10. **Releases (owner rulings 2026-09-08, 2026-09-09, 2026-10-05 D-030 B).** A verified fix goes live end to end and is reported after. An attended ship — a push, a merge, a release with a person in the chat — carries an independent-review trace before it ships: verdict, an independent reviewer, scope; `none — <reason>` allowed, silence never (the harness rule `independent-review-before-ship`). A new public page or link still needs a principal's explicit ask. A scheduled run with no person in the chat may release only when every automatic test passes, one change at a time; the storefront is excluded until it has automatic tests before release. This applies to every system, the ledger included. Storefront merges restart the live site: batch them, and wait for the site to be healthy before the next.
11. **Goals (owner rulings 2026-10-04, 2026-10-05, 2026-10-09).** A big goal is fine while it shows outcomes. A goal that runs for days with no visible outcome is split into small goals, one at a time, each with a finish line and a deadline. Principals give the outcome, the measure and the deadline; agents choose the how (owner ruling 2026-10-09, D-040). No numeric token caps. Every task ends in something a principal can open, or in a job leaving the principals' hands. Two habits: a fresh chat per task is packaging at handoff, never scheduling — agents cannot start a chat, so work moved to a later chat is postponed; executable work runs in the sitting that found it; reminders and checks stay cheap in tokens (never reload large instruction blocks every turn).
12. **Before a task.** Claim a multi-step goal in `varaledger/docs/memory/open-jobs.md` (join a live claim or pick another). Search past lessons for this problem first (`varaledger/docs/memory/learnings-index.md`, the website repo's `docs/company-brain/lessons/`), and check the cross-repo knowledge index for where a fact already lives (`vara-workspace/KNOWLEDGE-INDEX.md`; refresh sibling clones first — owner ruling 2026-10-11) and read the agent inbox (`vara-workspace/agent-inbox/to/<you>` — one command from the workspace clone: `node scripts/inbox.mjs pull list`; send with `node scripts/inbox.mjs send`) — owner ruling 2026-10-18; lessons are notes, never loaded by default and never rules. Then gather the skills, tools, access and information the job needs, and run it to the end. Access comes before instructions: standing bank-feed access, and a way for agents to start ZCode work themselves (owner ruling 2026-10-09, D-040).
13. **Evidence before claims.** Run the cheapest check that could prove a claim wrong before saying it works. A cause is "proven" only with the cause, a control and a number.
14. **Learn from failure.** On a failure or a correction: fix it, check the fix, record the lesson, and continue the original job the same turn. A new rule drawn from it is an agent inference (sources paragraph above).
15. **Agent watchdog (owner ruling 2026-10-05, D-030; live since the 2026-10-09 books restart, D-040).** Once a day Claude checks what ZCode did: bookings, releases, customer messages and rule changes. Big mistakes are flagged, ZCode reverses them and reports it, and a quiet day gives one line.
16. **Outside playbook (owner ruling 2026-10-05, D-030 C).** The Paziresh24 agents playbook is checked weekly. A new or changed rule there comes to the principals as a suggestion, labelled agent inference, and joins this rulebook only on a principal's yes.
18. **Close what you open in the browser (owner ruling 2026-08-25).** Every tab, window or debug profile an agent opens is closed by that session when its job ends; never a principal's own tabs; never kill the browser.
19. **Books writing and measure (owner rulings 2026-10-10, D-045, amended the same morning).** Rial top-ups and subscription charges are written by agents (the nightly run) with people typing the same lines in the Payments tabs as a cross-check. Each kind stops being typed only after 7 consecutive clean daily checks by Claude (no wrong agent entries of that kind; a wrong one resets the count); Claude's morning line reports the count and says when a kind can stop. An unidentified payer waits on a list worked daily, never an ask. Rial books are measured by bank coverage and waiting lines, never by matching the tab.

20. **Evaluate vs measure (owner ruling 2026-10-18, D-063).** Evaluating how something is going and measuring how it is going are different acts. Where a measurement would need crazy contortions, a direct evaluation — good taste and judgment, named as an evaluation, never dressed as a number — is the check. The floors hold: money, absence-of-evidence claims, owner-facing numbers, proven causes and the books measure stay measured (rules 8, 13, 19); verify outcomes keep their four statuses; overrun or spin still requires an independent check (the evidence discipline craft).

21. **Batching and brevity (owner corrections 2026-10-19, 2026-10-20).** Independent tool calls go in one message; a turn that makes three or more single-call requests which could have been batched is a defect. Replies are short by default, long only when a principal asked for a report. Exploration with three or more independent lookups goes to one subagent, not a chain of main-thread calls. The measure is batchable turns that were batched (owner correction 2026-10-20): a turn whose input does not depend on the previous tool result was batchable, and each batchable turn issued alone is a defect; a turn that needed the previous result counts neither way.

Bad: "I've been investigating the reconciliation issue. First I checked the tables, then ran the audit, and the pipeline showed…"
Good, same content in the principals' format:
- Outcome: all 14 unmatched deposits matched; £3,120 cleared.
- Concerns: two same-amount deposit pairs could be swapped; both are flagged for review.
- Open decision: how deposits are matched from next month. Recommendation: A.
  - A) Keep amount and date matching: no operator time; swap risk stays contained by the review queue.
  - B) Require a reference first: zero swap risk; a manual step on ~9 of 14 transfers.
  - Weighting: trust carried the most weight; cost near zero; speed medium.
  - Next step: reply A or B.

## Invariants

- Financial accuracy: ground-truth tolerance 0.02; base amounts use Math.round(amount * fx * 100) / 100.
- Scope every query, write and match by client_id/account_id/customer_id; keep tenants separate.
- D1 transactions are INSERT only; Sheets Ledger is append only. Preserve historical amounts and fx_rate.
- **Payments tab boundary (owner standing rule 2026-09-28, D-020):** the system may write the client workbooks' Ledger tab; it NEVER writes the Payments tab — no env var, no re-enable; the Apps Script refuses append_payments_row and never creates a Payments tab. Reads stay allowed; a workbook with no Payments tab is skipped and listed (never read from the first tab, Ledger, or any other tab).
- Receipt ingestion: append Sheets before inserting D1; abort if Sheets fails. Fetch and store FX once for new transactions.
- Preserve secrets; obtain explicit authorization for destructive remote actions and production money writes (standing authorization for held bank-feed payments since the books restart, 2026-10-09, D-040: owner ruling 2026-10-04, the business repo's `fpa/DECISIONS.md` D-028). Keep exploratory work in scratch/.
- **Query & Data Standard (non-deferrable):** Never create one-off search scripts (e.g. `find-xyz.ts`, `inspect-xyz.ts`). For ANY data lookup — searching transactions, finding client rows, auditing bank lines — use: `npm run query -- --term <term>` (parametric) OR `npm run query:sql -- "<SQL>"` (DuckDB/analytical SQL). For live Worker API data (staging rows, client ledger): `npm run query -- --client <AC-code> --source live`. One-off exploratory scripts go only in `scratch/` (gitignored). Creating a standalone search script when these tools exist is a harness violation; `npm run check:harness` will fail the pipeline.

## Working protocol

- **Bank transactions missing documents:** use `npm run docs:audit:bank -- --bank <approved-export.csv>`; repeat `--bank` for additional exports. Read [the audit entrypoint](docs/craft/bank-document-audit.md) once. Reuse its fingerprinted result for follow-up filters; do not create scratch matchers. Filename candidates are unverified and cannot assign clients. This offline path supersedes generic multi-source/OCR lookup for this task.
- **Missing-evidence claims are machine output, never recollection (owner challenge 2026-09-25, the 100th-time class):** any statement that bank evidence is absent — in a report, an ask, or the open-decision section — must be the machine's own enumeration (`npm run sources:inventory` coverage lines + the drawer diff + the D1 Revolut staging coverage from `staging_transactions` and `revolut_sync_state`), quoted at claim time, never copied from an earlier note of the same session. A book rebuild must enumerate the evidence drawer by machine FIRST and name every unconsumed statement-format file plus its fate (consumed per-rail / belongs to another book / reviewed-and-rejected with the reason). A file's NAME is not its content — a "wise-…" file holding Revolut rows is a proven trap; classify by header before trusting coverage numbers. The Revolut API rail is LIVE (6-hourly sync, last runs proven): staged rows are evidence HELD AND CURRENT, not missing — their ledger application: the books work restarted 2026-10-09 (D-040) — ZCode approves held payments whose customer and amount are certain, the rest stay waiting, and Claude checks the approvals afterwards (owner ruling 2026-10-04, the business repo's `fpa/DECISIONS.md` D-028).
- **Windows commands:** put nontrivial JavaScript/TypeScript in the maintained command rather than nested inline shell strings. After a quoting error, switch to a script file; do not retry variations of the same inline command.
- **Audit follow-ups:** use `npm run docs:audit:bank -- --reuse --summary` or its documented filters. Preserve the generated evidence labels and separate-currency totals; unresolved does not mean missing. A read-only summary request does not authorize code changes or an inline regrouping script.
- **Receipt review persistence:** inspect `--review-queue --details` and record actually inspected evidence with `--record-review` per the audit entrypoint. Preserve `data/receipt-reviews.json`; future commands recheck and reuse it. A report-only note is not a durable match fix.

- Read-only questions end with evidence and an answer. Implementation tasks follow the authorized test, commit and push workflow; scope staging to this task's files. A push to main releases the ledger: a scheduled run with no person in the chat pushes only when `npm run self-verify` is fully green, one change at a time (owner ruling 2026-10-05, D-030 B).
- Before implementation, consult the Autonomous Execution Protocol and Safety sections in [AGENT_REFERENCE.md](AGENT_REFERENCE.md). Before changing money, matching, FX or tenancy, also read its Domain knowledge base and relevant docs/principles/ and docs/kb/ sections.
- Process rules come from the portable harness; domain invariants above take precedence on financial safety. The reference's routing remains authoritative when a listed trigger applies.
- Await completion notifications for background commands and agents. Use at most one initial status check; another requires new evidence or an explicit status request. No timer-based polling.
- Use the smallest relevant context. First step of a task: search past lessons for this problem — start from `docs/memory/learnings-index.md` (one line per entry; pre-September entries live in `learnings-archive-2026-08.md`) and read only the matching entries. Lessons are notes, never loaded by default and never rules. Read a referenced file once unless it changes.
- Execute approved tasks autonomously to completion without unnecessary pauses; escalate only for missing essentials, conflicting requirements, or production money writes.
- Communication style: Be succinct, direct, and avoid buildup or conversational fluff.
- Read [AGENT_REFERENCE.md](AGENT_REFERENCE.md) by section for architecture, API contracts, domain docs, memory policy, evidence standards and delivery criteria. All original detailed guidance is preserved there with relative links unchanged.
